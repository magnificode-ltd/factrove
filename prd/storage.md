# Storage

## Purpose

Each installation stores artifact bytes in one S3-compatible bucket. The API is the only process that reads and writes that bucket. Web and CLI never receive bucket names, object keys, or storage credentials.

## Current behavior

The storage module has one implementation. It reads `S3_BUCKET` and `S3_REGION`. Optional `S3_ENDPOINT` selects an S3-compatible origin. When `S3_ENDPOINT` is unset, the client calls AWS S3 in `S3_REGION` with virtual-hosted addressing and ignores `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3`, and a profile `endpoint_url`. When `S3_ENDPOINT` is set, `S3_FORCE_PATH_STYLE` defaults to true and may be set to false. Plain `http://` is accepted only for `localhost`, `127.0.0.1`, and `::1`. Any other host requires `https://`, unless `S3_ALLOW_INSECURE_HTTP=true`. That flag sends the access key in cleartext and is for a private network only.

Static `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are optional and must be set together. Otherwise the SDK default chain, including `AWS_PROFILE`, is used. `AWS_SESSION_TOKEN` is optional with the static keys. The API does not create the bucket. `pnpm infra:up` starts Garage and creates the local bucket named by `S3_BUCKET`. An existing AWS bucket is `S3_BUCKET` and `S3_REGION` with `S3_ENDPOINT` unset.

The caller needs `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` on the object, and `s3:ListBucket` on the bucket. Without `s3:ListBucket`, a missing key comes back as access denied.

Object keys are generated by the API. The current HTML object is `{artifactId}/{contentId}.html`. Rows from before `object_key` existed use `{artifactId}.html`. The public filename stays `{artifactId}.html`. A content response takes the key and `Content-Length` from the same row snapshot.

A missing object is `BLOB_NOT_FOUND`. Configuration failures, storage outages, and any other storage error, including a generic HTTP 404, are `BLOB_STORE_UNAVAILABLE`. `delete` resolves when the object is already gone. Error messages omit bucket and credential values. The error cause is for server logs and is not sent to clients. The API maps storage failure to `503 STORAGE_UNAVAILABLE`. A failed create stores no artifact row. A failed delete can remove the object before the row delete fails, so a retry treats a missing object as already removed.

## Decisions

Database persistence stays PostgreSQL through Prisma. There is no second database provider and no Azure or GCP blob implementation. The S3 client is the seam for another S3-compatible service, selected with `S3_ENDPOINT`.

Files placed in the bucket outside Factrove are not imported. The upload and replace routes are the only ingestion paths. See [artifacts.md](artifacts.md) for the compare-and-set that publishes a new key.

`S3_INTEGRATION=1` runs the storage integration tests against the local Garage endpoint. Those tests require a loopback HTTP endpoint before they open a client.
